# typebulb/format

> This is the spec for the **bulb format**. For what bulbs are and how they're used, see the [Typebulb FAQ](https://typebulb.com/faq).

`typebulb/format` is the canonical definition of the format: parsing, serializing, the block registry, `config.json` types, and `data.txt` chunk splitting — shared by the CLI and typebulb.com so the two never diverge.

## The bulb format

A **bulb** is a single Markdown file (`.bulb.md`): YAML frontmatter, then a series of named **blocks**. Each block is a `**filename**` header on its own line followed by exactly one fenced code block.

````markdown
---
format: typebulb/v1
name: Counter
---

**code.tsx**

```tsx
import { createRoot } from "react-dom/client"
createRoot(document.getElementById("root")!).render(<h1>hi</h1>)
```

**index.html**

```html
<div id="root"></div>
```
````

The parser is deliberately tolerant: blank lines between a header and its fence are skipped, trailing whitespace on fences is allowed, a header with no following fence is ignored rather than fatal, and the fence length auto-grows so a block's own triple-backtick fences nest safely. The frontmatter `format:` is accepted as long as it starts with `typebulb` (version-tolerant).

## Blocks

| Kind | File | Purpose |
|------|------|---------|
| `code` | `code.tsx` | App logic and UI (TypeScript/TSX). See the [Code](#code) section below |
| `html` | `index.html` | HTML or HTML fragment. See the [HTML](#html) section below for more details |
| `css` | `styles.css` | Styles |
| `data` | `data.txt` | Read-only data the code processes (JSON/CSV/XML/YAML/text); chunks split on 2+ blank lines |
| `infer` | `infer.md` | Prompt for a one-shot runtime LLM call |
| `insight` | `insight.json` | Output of the `infer` call |
| `config` | `config.json` | Dependencies, description, inference settings (`BulbConfig`) |
| `notes` | `notes.md` | Persistent context for the AI assistant |

`server.ts` (server-side Node code) is also a valid block, but it is **CLI-only** — it runs locally and is stripped on import to typebulb.com — so it lives with the CLI, not in this package's registry.

## Code

`code.tsx` is the bulb's entry point. It runs as a native ES module in the browser: a normal top-level page when run standalone, a sandboxed iframe when embedded. What the code can count on:

* **TypeScript/TSX**, compiled to JS before it runs. JSX follows TypeScript's default of `react`; set `ts.jsxImportSource` in `config.json` for another runtime (e.g. `preact`).
* **Bare imports, nothing else.** Import npm packages by bare name at the top of the file (`import React from "react"`); the resolver ([`typebulb/resolver`](../resolver/src)) pins each dependency to a version and the type library ([`typebulb/dts`](../dts/src)) supplies its types. Every other form is prohibited: dynamic `import()`, `require()`, URL imports (`"https://…"`), version specifiers (`"react@18"`), `.js` on deep import paths, and file imports like `import "./styles.css"` (the `css` block is applied for you).
* **The DOM is live.** Mount into the element your `html` block declares, e.g. `createRoot(document.getElementById("root"))`.
* **`tb` is a pre-declared global** (no import), ready before the first line runs. Its authoritative shape is the `.d.ts` the CLI hands `tsc` on `npx typebulb check`, single-sourced in `typebulb/dts` ([`tbTypings.ts`](../dts/src/tbTypings.ts)). The `data` and `insight` blocks can be accessed with `tb.data()` / `tb.json()` / `tb.insight()`.
* **`tb.mode` tells you where you are**: `local` (CLI), `embedded` (sandboxed iframe), or `editor` / `published` (typebulb.com).
* **It runs in the browser**, and reaches the server through `tb.*`. In local mode you can add your own server-side code in a `server.ts` block; its exports are callable from the browser as `tb.server.<name>()`.
* **Logging.** `tb.log()` posts to the CLI and prints to its stdout (what `typebulb logs` reads back). Plain `console.log` and uncaught errors go to the browser console; an embedded bulb additionally forwards its runtime errors out to the host.

## HTML

The `html` block may be either an HTML fragment or a full HTML page. The former is much more common, e.g. a single mount element such as `<div id="root"></div>` for React. How the host splices the provided HTML into the final page is at its discretion, but the two cases have an obvious shape: a fragment is wrapped in a document scaffold (with `charset` and `viewport` meta added if absent); a full page is merged into, not replaced (the host keeps the user's `<head>` / `<body>` and adds its own pieces alongside). The host must minimally add:

* The user's CSS, plus a base stylesheet of its own (a reset, and `color-scheme` for light/dark).
* An import map, generated by the resolver.
* The `data` and `insight` blocks, exposed as the runtime values behind `tb.data()` / `tb.insight()`.
* The `tb.*` global, in place before the user's code runs. Missing methods may no-op or show a friendly message if a feature is unavailable, but should throw if permissions are not granted (e.g. an embedded bulb tries to call `tb.fs.read()` or call a custom method on `tb.server`)
* Theming stubs to support light and dark themes.
* The user's compiled code, run as a module (see [Code](#code) below).

## API

- **Registry** — `blocks`, `orderedKinds`, `kindFromPath`, types `SubscriptKind` / `SubscriptPath` / `BlockSpec`.
- **Parse** — `parseBulb(text) → ParsedBulb | null`, `toBulbData(parsed) → BulbData`.
- **Serialize** — `serializeBulb(source) → string`.
- **Config** — `parseConfig(json) → BulbConfig`, types `BulbConfig` / `InferenceConfig`.
- **Data chunks** — `splitIntoChunks` / `splitIntoChunksWithBoundaries`, `isStructuralData` (JSON/XML/YAML).
